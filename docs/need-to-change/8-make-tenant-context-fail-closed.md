# 8. 显式租户选择失败必须 fail closed

| 属性 | 结论 |
| --- | --- |
| 优先级 | P0 |
| 置信度 | 高 |
| 影响 | wrong-tenant 读写、撤权后短期继续操作、调用方非空断言崩溃 |

## 对抗判决

请求显式指定一个用户不属于的 active org 时，服务端记录 warning 后选择该用户的第一个组织继续执行。这把明确的上下文错误转换成另一个合法租户的写入。与此同时组织/角色缓存只按 userId 保存 60 秒，成员关系撤销和角色变更不会即时生效。

## 已核验证据

- `src/services/org-context.ts:25-35`：header > query > cookie 的租户选择优先级。
- `src/services/org-context.ts:17-18,44-47`：缓存 key 只有 userId，TTL 60 秒。
- `src/services/org-context.ts:53-93`：显式组织非成员时只告警，不拒绝。
- `src/services/org-context.ts:96-123`：随后取第一个组织并缓存。
- 大量 web routes 使用 `store.authContext!`；上下文为空/漂移由非空断言掩盖，未形成 handler 类型不变量。

## 架构诊断

认证主体与租户上下文被组合成可空、可回退的共享状态。route 看见的是“可能存在的 AuthContext”，却把它当作可靠 interface；成员校验、fallback 和缓存 implementation 没有表达失败语义。

## 目标不变量

- 请求显式提供 org 时：不存在、非成员、角色不可确认、校验服务异常都拒绝；绝不选择其他组织。
- 仅在客户端未选择 org 的首次引导流程中，才能显式返回“可选默认组织”，且不直接执行原业务写操作。
- TenantContext 包含可审计的选择来源、成员版本/更新时间和权限；route 获得它即代表验证完成。
- 缓存至少按 user+org 隔离，并在成员/角色变更时失效；高风险操作可绕过缓存或使用版本校验。
- auth plugin 在进入 handler 前保证上下文非空，类型上消除散落 `!`。

## 分阶段整改

1. 把显式 org 不匹配改为 403/404 的稳定错误契约，补 wrong-tenant 回归测试。
2. 把默认组织选择从普通业务请求中移到登录/引导流程。
3. 建立成员变更驱动的缓存失效和高风险授权重检。
4. 迁移 route 到经过验证的 TenantContext interface，删除非空断言。

## 验收与观测

- 同一用户有 A/B 组织时，伪造/过期/被撤销的 B 选择绝不落到 A。
- 撤权、降权后高风险操作在定义的传播时限内拒绝；传播时限有指标和告警。
- 日志同时记录 requestId、requestedOrg 与决策，但对客户端不泄露组织是否存在。

## 边界说明

这不是未认证用户跨租户读取的证明；准确后果是合法多组织用户的 wrong-tenant 操作，以及撤权窗口。严重性来自写入不可逆和审计归属错误。
