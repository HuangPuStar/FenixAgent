# ADR-0001：CE 分包迁移、逐包治理与 API 边界

- 状态：已接受；以本修订取代原“完整重构后单次切换”的交付决策。
- 影响范围：CE 迁移计划、第一方与外部 HTTP 合同、生产发布方式。

## 背景

原计划要求先完成 AgentConfig 最小闭环、再迁移其他模块、最后统一切换。物理拆包和新架构治理混在同一任务，容易误改既有权限、接口和业务行为，难以逐项审查。现有工程骨架和平台基础实现已经落地，但根 `src/`、`web/` 的业务逻辑尚未完成分包。

## 决策

1. **先做物理迁移**：按现有功能闭包逐个移动所有根 `src/`、`web/` 代码、测试和相关交付引用到 `apps/`、`packages/` 等最终归属；一个闭包一个提交。不改变任何现有业务行为、HTTP/API/协议合同、认证授权（包括原有 `resource_permission`）、数据库 schema、DDL、存量数据与迁移链。中间提交可以暂时不通过全量检查，但必须记录原因；阶段 1 最终提交须全绿、端到端可用并可上线。不为中间提交引入临时兼容逻辑。
2. **再逐包分析**：阶段 1 完成后，每个包根目录写简短 `refactor-plan.md`，仅记录优先适配的依赖包、自身治理事项与要保护的现有合同，不提前详细设计或修改业务。所有包都有该文件时结束阶段 2。
3. **最后逐包适配**：用户根据依赖和业务优先级决定顺序。每个包单独制定实施任务，审查合同/数据影响，按可上线 PR 交付；完成后删除该包的 `refactor-plan.md`，全部删完即完成治理。阶段间及包之间允许正常生产版本发布和业务迭代，不设全仓统一切换点。
4. **API 边界是目标，不是阶段 1 的变更许可**：第一方控制面最终以 `/web/*` 组织，已发布的 `/api/*` 作为外部稳定合同按协议独立评估；ACP、MCP、hooks、WebSocket 等沿用各自前缀。阶段 1 原样保留现有 method、路径、name/ID、请求/响应、错误和可用身份，包括已存在的 `/web/config/:module` action 风格。目标的稳定 ID、REST 资源路径、公开 Facade 与新权限体系仅在对应包的阶段 3 适配任务中，经影响确认后实施；任何已发布外部接口的停用须消费者盘点和单独协议决策。
5. 阶段 1 只移动 schema 定义源码、更新其生成引用，不生成有 DDL 差异的 migration；历史迁移产物及其执行顺序保持原样。阶段 3 若确需数据治理，则为**该包的一次可上线发布**设计渐进升级、现有数据核验和独立回滚/恢复，不假定旧生产版本一直冻结。

## 后果

阶段 1 的重点是可对照的行为等价，而不是提前落地设计文档的目标 DTO 或新授权；阶段 3 的发布和数据兼容必须按每个包的真实生产状态分别设计。历史 ARC-03 目标契约仍是未来适配的参考，但其中旧任务顺序和一次发布门禁不再约束实施。
