# Agent 输出可视化：四条承载路径的定位

> 状态：设计选型（2026-10-08）。本文只锁定**方向、边界与四条承载路径的定位**，不锁定组件字段级契约——组件目录与 props 在实现期随 skill 一起冻结。
> 范围：对话内「Agent 输出」的展示形态。核心是四条承载路径——**iframe / agent-sites 自定义卡片 / 声明式 UI Spec（借 json-render 的形状）/ MCP Apps**——各自的位置与分工；每条路径都写清「对 Fenix 的要求」「对 Agent 或提供方的要求」「用户得到什么」。
> 权威性：消息时间线、Y.Doc schema、投影与重连语义以 [19-yjs-chat-streaming](./19-yjs-chat-streaming.md) 为准；Markdown / 自定义标签 / iframe 的渲染与安全规则以前端开发规范 §6.1、§6.2 与 [05-chat](./05-chat.md) 为准；MCP Apps 的协议、沙箱与授权细节以 [Peri MCP Apps 接入设计](../design/2026-08-28-peri-mcp-apps-integration-design.md) 为准。
> 非目标：定义新协议栈；替代工具卡片、文件预览等既有渲染面。

## 1. 决策摘要

1. **主通道是声明式 UI Spec**：借 json-render 的分层做法（宿主定**组件目录**，模型只产**受目录约束的组件树 JSON**，渲染始终由宿主组件完成），不引其运行时。模型在助手消息文本里输出 ` ```ui-spec ` 围栏 JSON。
2. **目录取材以 peri-canvas（Cursor Canvas SDK 移植）为参照，实现一律自持**：它有什么能力，我们用自有组件做对应类型；不引包、不镜像 API、交互类不做（详见 §2.3）。
3. **iframe 是沙箱产物透传的应急手段**：能把工作区里的 HTML 成品透出来给用户看，**能用但无奈**——内容脱离消息、不跟主题、不受宿主控制，不作为承载契约。
4. **agent-sites 卡片是「一形态一前端组件」范式，唯一生产实例准备下架**：该范式成本随业务形态线性增长，不再作为承载手段。
5. **MCP Apps 是未来的能力上限通道**：第三方应用在沙箱里运行，换来真实交互与生态复用，代价是信任面、审核成本与不可回放。
6. **四者的排序依据是「渲染器在谁的信任域执行」**，不是内容格式：宿主域（前三条）+ 沙箱域（MCP Apps）。声明式的 spec 是内容层，宿主域与沙箱域都能渲染。
7. **不可信输入、可回放、不新增越权面**这三条硬约束决定主通道归属。

## 2. 四条承载路径

### 2.1 iframe：沙箱产物透传（现状，能用但无奈）

**现状机制**：Agent 把 HTML 写进工作区文件，再在消息里写 `<iframe src="./user/report.html">`；宿主把工作区相对路径改写成文件代理 URL，由 `IframePreview` 渲染。`data:` 内联文档也在放行之列（离线示例与内联 HTML 预览在用）。安全基线固定：`sandbox="allow-scripts allow-popups"` 不可覆盖、`src` 过协议白名单、先做控制符规范化再校验。

**为什么无奈**：内容**不在消息里而在文件系统或远端**——不可回放（文件被改、被删、鉴权失效即空白）、不跟宿主主题与版式、尺寸与交互不受控、样式与产品其他部分不一致。它本质上是「把一份 HTML 成品塞进对话」，不是「让 Agent 表达结构」。

**定位**：应急手段。用户确实需要看某个 HTML 文件时保留它；**不把它当承载契约，也不鼓励 Agent 靠造页面来表达信息**——那部分应当由组件目录承载。

### 2.2 agent-sites 卡片：宿主专有组件范式（现状，准备下架）

**现状机制**：宿主开发者用 `registerTagRenderer` 把 kebab-case 标签注册成自己的 React 组件，注册表**默认空**（未注册标签会被 rehype-sanitize 剥离，安全默认），注册时一并声明属性白名单；卡片可用 `CardEventEmitter` / `useCardEmit` 把交互抛回宿主。生产环境**唯一实例是 `agent-sites`**（其余都是 demo 与测试）。

**范式的问题**：一个形态 = 一份前端组件代码 + 一次发版 + 一套属性白名单；形态数量随业务线性增长，而标签属性都是字符串，表达能力又很弱。相比之下，声明式通道用**一份目录**覆盖 N 种展示，扩展是加类型而不是加发版。

**定位**：范式退场。展示类需求交给声明式通道；卡片独有的「交互回传」在只读通道里没有对等物，但这类需求本身少数，且未来有 MCP Apps 承接（§2.4）。

### 2.3 声明式 UI Spec：借 json-render 的形状（本期主通道）

**借的是什么**：json-render 把 Generative UI 拆成三层的做法——**允许用什么（组件目录）→ 模型产什么（受目录约束的组件树 JSON）→ 怎么渲染（宿主自己的组件）**。我们借这三层与 Spec 的形状（`{ version, root, elements }` 扁平树，元素 `{ type, props, children }`），**不引其运行时**：不要数据绑定与 actions（只读展示用不上，还会引入求值语义与授权模型），也不要它的流式 patch（Spec 是消息内容，随 Y.Doc 落盘、按消息回放，单 JSON 足够）。

**对 Fenix 的要求**

1. **维护组件目录**：一份允许 Agent 使用的类型清单 + 每个类型的参数约束，随设计系统演进；目录对外是产品契约，不是实现细节。
2. **提供宿主实现**：每个类型有对应宿主组件（复用既有 primitives 与图表能力），跟主题、暗色、响应式、i18n 与无障碍。
3. **校验与降级管线**：结构、字段、限额逐层校验；坏输入降级为原文、未知类型降级为占位——任何一条都不能把消息渲染搞崩。
4. **提示词资产与同步**：把目录写给 Agent（随 skill 交付），并用同步测试钉住「代码目录 ↔ 文档目录」一致。
5. **版本与回滚**：类型只增不改（破坏性变更换新类型名）；注册点单一，撤销即恢复现状。

**对 Agent 的要求**

1. **只产数据**：选组件、填参数、编排子节点；不写代码、不发请求、不做表达式与绑定。
2. **严格按目录**：只用目录内的类型名与必填字段；拿不准就退回文字描述，不硬凑组件。
3. **一个围栏块输出完整 JSON**：便于校验、降级与回放。

**用户得到什么**

1. **回答按内容出形状**：KPI、趋势、对比、明细、流程各有其形，而不是一堆表格与文字。
2. **与产品一致**：跟随主题与暗色模式、响应式、可访问、可翻译——和页面其他部分是同一套设计系统。
3. **可回放、可复制、可引用**：历史消息重新打开仍是同一张图（数据就在消息里，不依赖远端页面或文件）。
4. **不用打开文件、不用看 HTML、不用截图。**

**代价（诚实写）**：只能表达目录覆盖的形状，做不了任意网页、动画或 3D；目录扩张需要前端投入；v1 只读，交互需求走外链或未来的沙箱应用。

**目录取材：以 peri-canvas 为参照，用自己的组件做**

`peri-canvas`（Cursor Canvas SDK 的独立 React 移植）只提供**能力盘点参照**——它有什么能力，我们就用**自有组件**实现对应类型。它是参照，不是依赖：不引它的包、不镜像它的 API、不跟它的升级节奏；它的 MCP App 载体（`show_canvas` + `ui://` 资源）也不是我们的渲染通道（通道问题见 §2.4）。完整取材清单、每个类型怎么做、以及怎么与 json-render 搭配，见 **§5**。

另外，它给 Agent 写的 authoring rules 值得直接借鉴进我们的 skill：数据内联、禁止 `fetch`、不渲染空状态、图表必须标注坐标轴与单位、来源与时间范围、避免一列同构卡片堆叠——这些与上文「对 Agent 的要求」完全同向。

### 2.4 MCP Apps：第三方应用在沙箱里执行（未来）

**它是什么**：MCP 官方扩展。第三方 MCP server 提供一个 HTML 应用，宿主把它放进沙箱 iframe 运行，双方按 MCP 协议双向通信（包括应用发起的工具调用）。挂载点是**工具调用卡片**：App 实例化的工具成功后，同一张卡片渲染为交互式 View。

**对 Fenix 的要求（成为 MCP host）**

1. **沙箱与资源分发**：跨源沙箱、应用资源可加载；宿主凭据、绑定信息、临时令牌**永不进入 iframe**。
2. **桥与生命周期**：宿主侧负责应用握手、消息桥、工具调用回调与销毁；不把本地快照当授权，每次调用回到真实策略。
3. **权限与审核**：能力最小化（摄像头、剪贴板、网络等按产品审批）、CSP 与 Permissions Policy 默认拒绝、按 App 审核与灰度。
4. **可观测与撤销**：App 调用可审计；权限或会话失效即 fail closed。
5. **生态前提**：平台要能作为 MCP host 连接第三方 server（今天 MCP 只做配置与探活）。

**对 Agent / 提供方的要求**

1. MCP server 提供并声明 UI 资源与应用元数据（尺寸、所需权限）。
2. App 作者遵守协议、沙箱约束与主题约定（尺寸变化、明暗模式）。
3. Agent 只负责「调用触发 App 的工具」，不参与渲染。

**用户得到什么**

1. 对话内能用**真实的交互应用**：表单、仪表盘、多步流程，而不是只能看的图。
2. 能力来自**第三方生态**：Fenix 前端不必为每个业务形态开发组件。
3. **跨宿主复用**：同一 App 在 Claude / ChatGPT / Cursor / VS Code 等宿主通用。
4. 若做成「渲染器型 App」（通用渲染器 + 目录，内容仍是组件树 JSON），**同一份 Agent 输出可以跨宿主复用**——代价是外观由 App 决定，不再跟随本产品设计系统。

**代价**：执行第三方代码，需要沙箱、审核、权限与审计，信任面与成本都最高；应用与宿主会话绑定，失效即关闭，**历史消息不复现**（数据可留，运行环境不留）。

## 3. 承载路径对照

| 路径 | 内容形态 | 对 Fenix 的要求 | 对 Agent / 提供方的要求 | 用户得到什么 | 现状 |
| --- | --- | --- | --- | --- | --- |
| iframe | 一个指向工作区 HTML（或 `data:` 文档）的 URL | 文件透传 + 固定 sandbox + 协议校验 | 写文件并在消息里引用 | 能看到 HTML 成品（应急，无契约） | 已实现 |
| agent-sites 卡片 | 标签 + 字符串属性 | 每个形态写一个前端组件并注册（发版） | 按已知标签填属性 | 与业务系统联动的固定卡片 | 唯一实例准备下架 |
| **声明式 UI Spec** | **组件树 JSON** | 组件目录 + 宿主实现 + 校验降级 + 提示词同步 | 只选组件、填数据，不写代码 | 跟主题、可回放、按内容出形状的展示 | **待实现（本文选定）** |
| MCP Apps | 第三方应用（HTML）或渲染器 + spec | 成为 MCP host：沙箱、桥、权限审核、fail closed | 提供 App 与 UI 资源，遵守协议 | 对话内可用的真实交互应用，且能跨宿主复用 | 已设计，待实施 |

控制权梯度（按「渲染器在谁的信任域执行」排序）：

```
模型写 URL      模型写标签       模型写组件树        第三方写代码
  iframe      agent-sites 卡片   声明式 UI Spec      MCP Apps
 ├──────────── 宿主控制力递减 / 表达力递增 ────────────┤
  产物透传(应急)  宿主专有形状(退场)  受控的自由        第三方应用
```

最后一档的位置可变：**渲染器型 App 里跑的仍然是声明式 spec**，只是渲染器搬进了沙箱——所以排序看的是渲染域，不是内容格式。

## 4. 为什么主通道是声明式

**相对 iframe**——分界在「内容在哪」。iframe 的内容在文件系统或远端，随时可变、无法回放、不受宿主控制；声明式的 Spec 就在消息里，可校验、可主题化、可重渲染出同一结果。要让"能表达的东西"由组件目录承载，而不是让 Agent 造页面。

**相对 agent-sites 卡片**——分界在「扩展成本」。卡片是一形态一组件、一次发版；声明式用一份目录覆盖 N 种展示。卡片范式退场后，展示类需求没有理由再走它。

**相对 MCP Apps**——分界在**渲染器在谁的信任域执行**：

| 取舍项 | 宿主域渲染（本期主通道） | 沙箱域渲染（渲染器型 App） |
| --- | --- | --- |
| 组件与外观 | 宿主组件库，跟随设计系统与主题 | App 自带（如 shadcn），外观由 App 决定 |
| 第三方代码 | 无 | 有（沙箱 + CSP + 权限审批 + 审核） |
| 可回放 | 是（Spec 就是消息内容） | Spec 可回放，运行环境不保证 |
| 组件丰富度 | 受宿主目录限制 | 由 App 决定，可超出宿主目录 |
| 跨宿主复用 | 只在本产品内 | 同一份 spec 可被第三方宿主渲染 |

判定规则：**只读展示、宿主自有产品 → 宿主域；跨宿主复用或需要第三方能力/组件库 → 沙箱 App。** 应用型 App（自带业务逻辑）只在工具卡片上，与本文通道不重叠。一句话分工：**「看起来是这样」用声明式，「用起来是这样」用沙箱应用，「到别人的宿主里也得看起来是这样」用渲染器型 App。**

**顺带排除的两个近路**：

- 把 Spec 塞进 `<iframe srcdoc>`：iframe 里没有宿主 React 运行时，要用宿主组件就得把组件库搬进沙箱；且内容脱离消息文本，可回放与主题跟随一起丢掉。
- 把 JSON 塞进自定义标签属性：标签属性都是字符串，体积、转义、流式与校验都不成立。

## 5. 组件目录：怎么做、怎么与 json-render 搭配

### 5.1 一条类型的生产线

| 步 | 做什么 | 判定标准 |
| --- | --- | --- |
| 1 | **定语义**：这份输出在对话里回答什么问题（趋势 / 明细 / 步骤 / 差异） | 语义说不清就不进目录（宁缺毋滥） |
| 2 | **定参数**：用 `zod/v4` 写 props——只收数据（字面量），枚举穷尽（tone 之类），数组与字符串有上限，容器类才有 `children` | **不收样式**：没有 className / style / 颜色 / 尺寸；模型不能控制视觉 |
| 3 | **写宿主组件**：复用 `@fenix/ui-components/ui/<name>` 与既有 primitives | 只读 props、不发请求、不做业务取数；跟随主题、暗色、响应式、i18n、无障碍 |
| 4 | **注册**：`type → 组件` 的映射 | 模块级常量，避免击穿 memo |
| 5 | **接线校验与降级**：结构 → 目录 zod → 限额 | 坏输入降级原文、未知类型降级占位，不崩整条消息 |
| 6 | **写提示词**：类型名、用途、必填字段、一个最小示例，随 skill 交付 | 双向同步测试钉住「代码目录 ↔ 文档目录」一致 |
| 7 | **测试**：正常 Spec、异常 Spec（未知类型 / 超限 / 非法 URL）、历史回放一致性 | 降级路径必须被覆盖 |

### 5.2 一个例子：把借鉴落成类型（Diff）

```ts
// ① 目录条目（catalog.ts）：纯数据，无框架耦合
Diff: {
  props: z.object({
    path: z.string().max(200).optional(),
    patch: z.string().max(16_000), // unified diff 文本，组件内解析成行
  }),
}
```

```tsx
// ② 宿主组件（components/diff.tsx）：只读渲染，样式全走设计系统 token
export function DiffView({ path, patch }: DiffProps) {
  return (
    <div className="rounded-md border bg-muted/30">
      {path ? <div className="border-b px-3 py-1.5 text-xs text-muted-foreground">{path}</div> : null}
      <pre className="overflow-x-auto px-3 py-2 text-xs">{renderUnifiedDiff(patch)}</pre>
    </div>
  );
}
```

```jsonc
// ③ 模型产出（助手消息里的 ui-spec 围栏片段）
{ "elements": { "d1": { "type": "Diff", "props": { "path": "src/app.ts", "patch": "@@ -1,3 +1,4 @@\n-old\n+new" } } } }
```

要点：数据内联（patch 就是文本）、样式不在 props 里、解析在组件内且只产出文本节点——这三条对所有类型都成立。

### 5.3 与 json-render 的搭配

| json-render 概念 | 我们的落地 | 搭配方式 |
| --- | --- | --- |
| **catalog**：`defineCatalog(schema, { components })`，类型 + zod props，`catalog.prompt()` 生成系统提示词 | 同样一张「类型 → zod props」表，放在 `catalog.ts` | **保持同形、不调它的 API**：切换时把它套上去零改写 |
| **spec**：`{ root, elements }`，元素 `{ type, props, children }` | 同类扁平树，我们多加一个 `version` | 我们的 Spec 是它的**合法子集**（无 `$` 指令、无 actions）→ 单向兼容 |
| **registry**：`type → 平台组件` | 我们的注册表，值就是 React 组件 | 组件是普通 React 组件 → 可原样交给它的 `Renderer` |

搭配分三级，由轻到重，**随时可停在任何一级**：

1. **形状对齐（现状）**：不引依赖，只保证 Spec 与目录同形。
2. **契约可导出（随时）**：目录是纯数据、组件是普通 React 组件——需要时交给它的 `defineCatalog` + `Renderer` 即可，**渲染层整体替换，Agent 提示词与历史消息不动**。
3. **整层替换（未来）**：若引入其运行时能拿到额外收益（如流式增量渲染），替换我们的校验与渲染实现；代价是多一个依赖与升级面。

搭配时要守的边界：

- `version` 是我们的**扩展字段**：导出给它的 Spec 只取 `root` 与 `elements`，`version` 留在我们的包装层。
- **限额由我们先校验**：不假设它能替我们挡住超限输入。
- **单向兼容**：我们产的 Spec 它一定能渲染；它带绑定与 actions 的 Spec 不是我们的 Spec（我们只读）。

### 5.4 取材清单（peri-canvas → 我们的类型）

| 它的能力项 | 我们怎么做（类型 → 实现 → 数据形状） | 判定 |
| --- | --- | --- |
| 布局与排版（Stack / Row / Grid / Spacer / Divider、H1–H3 / Text / Link / Code / Pill / Callout） | `Stack` / `Grid` / `Separator`、`Heading` / `Text` / `Link` / `CodeBlock` / `Badge` / `Callout`；基于既有 primitives，间距与字号由设计系统固定 | 做 |
| 卡片与统计（Card / CardHeader / CardBody、Stat） | `Card`（用 title / description 表达头体，不拆组件）+ `Metric`（label / value / delta / trend） | 做 |
| 表格（Table） | `Table`（columns / rows / caption / align，单元格仅字符串，宽表横向滚动） | 做 |
| 图表（BarChart / LineChart，手绘 SVG） | `BarChart` / `LineChart`：props 为 `x: string[]` + `series: [{ name, values: number[] }]`，复用 `ChartContainer`（recharts） | 做（重写，不复制视觉） |
| 用量条（UsageBar） | 由 `Progress` 扩展多段：`segments: [{ label, value, tone? }]` | 有真实用例再做 |
| 差异视图（DiffView / DiffStats） | 新增 `Diff`：`{ path?, patch }`，见 §5.2 | 值得做 |
| 待办清单（TodoList / TodoListCard） | `Steps` 的只读版：`items: [{ title, status, description? }]`；勾选交互不做 | 做只读 |
| 饼图（PieChart）、折叠区（CollapsibleSection）、色板（Swatch） | 需要时按设计系统新增（折叠可先用 `Callout` 形态） | 缺真实用例，先不做 |
| 依赖图（computeDAGLayout） | 新增 `Flow`（节点 + 边），布局在宿主算——参考其算法思路，不复用代码 | 待评估 |
| 表单与按钮（Checkbox / Select / TextInput / TextArea / Toggle / IconButton / Button） | — | **不做**：只读通道没有对等物，交互走既有面板或未来的沙箱应用 |
| 主题 tokens / palette、宿主 hooks（`useHostTheme` / `useCanvasState` / `useCanvasAction`） | 主题由宿主自动注入；状态与动作不引入 | **不借鉴**：那是「写代码」的能力面 |

三条原则：**按能力面取材、按语义建类型**（不照抄它的组件粒度与样式自由——inline style / className / Tailwind 一律不要）；**实现一律自持**（命名与参数服从我们的设计系统与既有 primitives）；**交互不做**。

## 6. 落地与边界

**切片**

1. **切片 1**：打通端到端——消息文本 ` ```ui-spec ` 围栏 → 校验 → 宿主组件渲染 → 降级；目录先给最小集合（容器 + 文本 + 表格），验证链路与提示词。
2. **切片 2**：扩目录（指标、图表、步骤等）并随 skill 交付给 Agent（同步测试钉住漂移）；评估增量渲染。
3. **切片 3+**：目录持续演进；若出现「同一份 spec 要在第三方宿主渲染」的需求，再评估渲染器型 App；应用型 App 按 MCP Apps 独立设计的节奏推进，与本通道互不阻塞。在此之前不引入第三方运行时与新依赖。

**边界与不变量**

- **不可信输入**：Spec 是模型产物。字符串一律走文本节点，无 `dangerouslySetInnerHTML`、无 `rehype-raw`；URL 过协议校验（与既有 iframe `src` 校验同口径）；组件不发请求；环境上下文（`envId` 等）只能由宿主注入，不能从 Spec 读取。
- **目录即契约**：组件类型只增不改（破坏性变更换新类型名），保证历史消息长期可渲染。
- **降级优先**：校验失败 / 未知组件 / 版本过新 → 降级为原始 JSON 或占位，不整体崩、不静默丢内容；降级可计数、可定位。
- **围栏与折行容错**（2026-10-09 补，事故驱动）：渲染前给**未闭合的 `ui-spec` 围栏**在首个平衡 JSON 结束处补闭标记——CommonMark 下未闭合块会吞掉其后全部正文，补全让 JSON 回围栏内、说明文字回正文；只插入不删改，流式不补。`JSON.parse` 失败后**仅**重试一次「删除字符串字面量内裸换行」（定宽环境复制的文本会带硬折行）。除此之外仍不补括号、不猜半截内容。
- **可回滚**：注册点单一，撤销注册即退化为普通代码块（现状）。

## 7. 风险与开放问题

| 项 | 说明 | 处理 |
| --- | --- | --- |
| 提示词漂移 | 交付给 Agent 的目录文档与代码目录可能不一致 | 双向同步测试钉住 |
| 模型不守约 | 非法 JSON、超限、越界字段 | 校验 + 降级 + 诊断计数 |
| 数据膨胀 | Spec 进入消息文本并随 Y.Doc 持久化 | 限额（量级在实现期由测试钉住） |
| 小屏与可访问性 | 宽表、多序列图表在小屏退化 | 宿主组件自适应；图表给文本替代 |
| 卡片退场后的承接 | `agent-sites` 下架后，站点结果的告知与入口由谁承载 | 由产品决策；若走本文通道，需评估目录内类型是否够用 |
| 与 MCP Apps 的重叠 | 同一展示既能宿主域渲染、又能做成渲染器型 App | 按 §4 判定渲染域：只读展示、宿主自有产品走宿主域 |
| 生态收敛 | json-render / A2UI 的标准化速度未知 | 形状对齐 + 实现可替换，不押注单一生态 |
