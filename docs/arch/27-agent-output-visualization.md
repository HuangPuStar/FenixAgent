# Agent 输出可视化：四条承载路径的定位

> 状态：设计选型（2026-10-08，2026-10-29 修订）。本文只锁定**方向、边界与四条承载路径的定位**，不锁定组件字段级契约——组件目录由 `@peri-code/sdk@0.3.0` 提供，宿主不自持。
> 修订说明（2026-10-29）：声明式通道不再自研。围栏语言由 `ui-spec`（JSON 组件树）改为 `openui`（OpenUI Lang 程序）；解析、组件库、渲染器与服务端系统提示词统一交给 `@peri-code/sdk` 的 OpenUI 能力；内置技能由 `ui-spec` 改名为 `openui`，旧围栏只按普通代码块做历史兼容。
> 范围：对话内「Agent 输出」的展示形态。核心是四条承载路径——**iframe / agent-sites 自定义卡片 / OpenUI 声明式通道 / MCP Apps**——各自的位置与分工；每条路径都写清「宿主/平台要做什么」「Agent 或提供方要做什么」「用户得到什么」。
> 权威性：消息时间线、Y.Doc schema、投影与重连语义以 [19-yjs-chat-streaming](./19-yjs-chat-streaming.md) 为准；Markdown / 自定义标签 / iframe 的渲染与安全规则以前端开发规范 §6.1、§6.2 与 [05-chat](./05-chat.md) 为准；MCP Apps 的协议、沙箱与授权细节以 [Peri MCP Apps 接入设计](../design/2026-08-28-peri-mcp-apps-integration-design.md) 为准。
> 非目标：定义新协议栈；替代工具卡片、文件预览等既有渲染面。

## 1. 决策摘要

1. **主通道是 OpenUI**：OpenUI Lang 的解析、组件目录、渲染器与服务端提示词都由 `@peri-code/sdk` 提供；宿主只做围栏切分、懒加载、主题桥与动作回传。模型在助手消息文本里输出一个 ` ```openui ` 围栏程序。
2. **组件目录归 SDK，宿主不复制**：不再自研 catalog / registry / parse / spec，也不维护 `ui-spec` 围栏与技能；升级 SDK 即更新组件目录，宿主只钉版本（当前 `0.3.0`）。
3. **iframe 是沙箱产物透传的应急手段**：能把工作区里的 HTML 成品透出来给用户看，**能用但无奈**——内容脱离消息、不跟主题、不受宿主控制，不作为承载契约。
4. **agent-sites 卡片是「一形态一前端组件」范式，唯一生产实例准备下架**：该范式成本随业务形态线性增长，不再作为承载手段。
5. **MCP Apps 是未来的能力上限通道**：第三方应用在沙箱里运行，换来真实交互与生态复用，代价是信任面、审核成本与不可回放。
6. **四者的排序依据是「渲染器在谁的信任域执行」**，不是内容格式：宿主域（前三条）+ 沙箱域（MCP Apps）。OpenUI 程序是内容层，宿主域与沙箱域都能渲染。
7. **不可信输入、可回放、不新增越权面**这三条硬约束决定主通道归属。

## 2. 四条承载路径

### 2.1 iframe：沙箱产物透传（现状，能用但无奈）

**现状机制**：Agent 把 HTML 写进工作区文件，再在消息里写 `<iframe src="./user/report.html">`；宿主把工作区相对路径改写成文件代理 URL，由 `IframePreview` 渲染。`data:` 内联文档也在放行之列（离线示例与内联 HTML 预览在用）。安全基线固定：`sandbox="allow-scripts allow-popups"` 不可覆盖、`src` 过协议白名单、先做控制符规范化再校验。

**为什么无奈**：内容**不在消息里而在文件系统或远端**——不可回放（文件被改、被删、鉴权失效即空白）、不跟宿主主题与版式、尺寸与交互不受控、样式与产品其他部分不一致。它本质上是「把一份 HTML 成品塞进对话」，不是「让 Agent 表达结构」。

**定位**：应急手段。用户确实需要看某个 HTML 文件时保留它；**不把它当承载契约，也不鼓励 Agent 靠造页面来表达信息**——那部分应当由 OpenUI 目录承载。

### 2.2 agent-sites 卡片：宿主专有组件范式（现状，准备下架）

**现状机制**：宿主开发者用 `registerTagRenderer` 把 kebab-case 标签注册成自己的 React 组件，注册表**默认空**（未注册标签会被 rehype-sanitize 剥离，安全默认），注册时一并声明属性白名单；卡片可用 `CardEventEmitter` / `useCardEmit` 把交互抛回宿主。生产环境**唯一实例是 `agent-sites`**（其余都是 demo 与测试）。

**范式的问题**：一个形态 = 一份前端组件代码 + 一次发版 + 一套属性白名单；形态数量随业务线性增长，而标签属性都是字符串，表达能力又很弱。相比之下，OpenUI 用**一份 SDK 目录**覆盖 N 种展示，扩展是加组件而不是加发版。

**定位**：范式退场。展示类需求交给 OpenUI；卡片独有的「交互回传」在 OpenUI 里由表单 + 按钮动作承接，更复杂的应用型交互留给 MCP Apps（§2.4）。

### 2.3 OpenUI：SDK 承载的声明式通道（本期主通道）

**分工**：OpenUI Lang 是逐行赋值（`identifier = Expression`）的声明式语言，SDK 负责把程序解析成 React 组件树。宿主与 SDK 的职责边界固定：

**宿主职责**

1. **围栏切分**：`splitOpenUI(text, streaming)` 只做 O(n) 行扫描，不解析 DSL。只接受一个顶层 ` ```openui `（或 `openui-lang`）围栏；多个顶层围栏整体回退 Markdown；流式未闭合时把已到达的片段交给渲染层；流结束后的裸程序只以 `root = Stack(` 开头识别。
2. **懒加载**：`OpenUIBlock` 是轻量静态入口，经 `lazy()` 加载 `OpenUIRenderer`；解析器、组件库与图表不得进入聊天入口 chunk。
3. **主题桥**：`installOpenUITheme()` 只读 `--chat-code-bg` / `--chat-fg` / `--chat-link` 三个 CSS 变量（hex），映射为 SDK 的 editorBackground / editorForeground / primary；暗色由宿主 `light` / `dark` class 或系统偏好决定，非 hex 值回退 SDK 调色板。
4. **动作回传**：`OpenUIActionProvider` 注入 `send`；`composeOpenUIActionMessage()` 把 `humanFriendlyMessage` 与 `formState` 拼成用户消息，`openExternalUrl()` 只放行 http(s) 后在新标签页打开。
5. **历史消息兼容**：旧 `ui-spec` 围栏没有渲染器，按普通代码块展示；不做数据迁移。

**SDK 职责**

1. OpenUI Lang 解析、流式渲染（节流后取最近一次可解析版本）与错误边界。
2. 32 个组件的实现、props 校验与主题样式：布局与文本 12 个、容器与数据 8 个、指标与图表 6 个、表单与动作 6 个。
3. 表单字段绑定与按钮动作（`@ToAssistant` / `@OpenUrl`）。
4. 服务端系统提示词 `generateOpenUISystemPrompt()`，随 SDK 版本发布。

**不再维护**：自研 `catalog.ts`、`registry.tsx`、`parse.ts`、`spec.ts`、`UISpecBlock` 渲染链，以及 `ui-spec` 围栏和内置技能。宿主不再校验程序结构，也不做版本号与限额判定——这些由 SDK parser 与 zod props 校验承担。

**安全边界**

1. 程序里的字符串一律作文本节点渲染，不执行任意脚本、不解析 HTML。
2. 点击动作只允许 http(s) 外链；`javascript:` / `data:` 等协议在宿主侧直接拒绝。
3. 表单值随用户消息发送，由模型按消息内容解释；不写回宿主状态，也不是授权凭据。
4. 渲染只读消息数据，组件不发请求；环境上下文由宿主注入，程序不能读取或覆盖。

**对 Agent 的要求**

1. 默认用普通 Markdown；只有结构化明显更优时才输出 OpenUI。
2. 一次只产一个完整程序，第一行 `root = Stack([...])`；参数按位置传，不用命名参数。
3. 只用目录内的 32 个组件与枚举值；拿不准退回文字。

**用户得到什么**

1. **回答按内容出形状**：指标、趋势、对比、明细、状态与 Todo 各有其形。
2. **与产品一致**：跟随主题与暗色模式、响应式与无障碍——组件样式由 SDK 与宿主 token 共同决定。
3. **可回放**：程序就在消息文本里，历史消息重新打开仍是同一结果。
4. **表单可回传**：字段值随按钮动作回到对话，由模型继续处理。

**代价（诚实写）**：表达力受 SDK 目录限制（32 个组件），做不了任意网页、动画或 3D；升级 SDK 需要回归历史消息渲染；动作只有「发消息」与「开外链」，没有自定义回调。

### 2.4 MCP Apps：第三方应用在沙箱里执行（未来）

**它是什么**：MCP 官方扩展。第三方 MCP server 提供一个 HTML 应用，宿主把它放进沙箱 iframe 运行，双方按 MCP 协议双向通信（包括应用发起的工具调用）。挂载点是**工具调用卡片**：App 实例化的工具成功后，同一张卡片渲染为交互式 View。

**对 Fenix 的要求（成为 MCP host）**

1. **沙箱与资源分发**：跨源沙箱、应用资源可加载；宿主凭据、绑定信息、临时令牌**永不进入 iframe**。
2. **桥与生命周期**：宿主侧负责应用握手、消息桥、工具调用回调与销毁；不把本地快照当授权，每次调用回到真实策略。
3. **权限与审核**：能力最小化（摄像头、剪贴板、网络等按产品审批）、CSP 与 Permissions Policy 默认拒绝、按 App 审核与灰度。
4. **可观测与撤销**：App 调用可审计；权限或会话失效即 fail closed。
5. **生态前提**：平台要能作为 MCP host 连接第三方 server（今天 MCP 只做配置与探活）。

**对 Agent / 提供方的要求**

1. MCP server 提供并声明 UI 资源与应用元数据（尺寸、所需权限）。
2. App 作者遵守协议、沙箱约束与主题约定（尺寸变化、明暗模式）。
3. Agent 只负责「调用触发 App 的工具」，不参与渲染。

**用户得到什么**

1. 对话内能用**真实的交互应用**：表单、仪表盘、多步流程，而不是只能看的图。
2. 能力来自**第三方生态**：Fenix 前端不必为每个业务形态开发组件。
3. **跨宿主复用**：同一 App 在 Claude / ChatGPT / Cursor / VS Code 等宿主通用。
4. 若做成「渲染器型 App」（通用 OpenUI 渲染器 + 组件目录，内容仍是 OpenUI 程序），**同一份 Agent 输出可以跨宿主复用**——代价是外观由 App 决定，不再跟随本产品设计系统。

**代价**：执行第三方代码，需要沙箱、审核、权限与审计，信任面与成本都最高；应用与宿主会话绑定，失效即关闭，**历史消息不复现**（数据可留，运行环境不留）。

## 3. 承载路径对照

| 路径 | 内容形态 | 对 Fenix 的要求 | 对 Agent / 提供方的要求 | 用户得到什么 | 现状 |
| --- | --- | --- | --- | --- | --- |
| iframe | 一个指向工作区 HTML（或 `data:` 文档）的 URL | 文件透传 + 固定 sandbox + 协议校验 | 写文件并在消息里引用 | 能看到 HTML 成品（应急，无契约） | 已实现 |
| agent-sites 卡片 | 标签 + 字符串属性 | 每个形态写一个前端组件并注册（发版） | 按已知标签填属性 | 与业务系统联动的固定卡片 | 唯一实例准备下架 |

```

  iframe      agent-sites 卡片      OpenUI 通道        MCP Apps
 ├──────────── 宿主控制力递减 / 表达力递增 ────────────┤

最后一档的位置可变：**渲染器型 App 里跑的仍然是 OpenUI 程序**，只是渲染器搬进了沙箱——所以排序看的是渲染域，不是内容格式。

## 4. 为什么主通道是 OpenUI

**相对 iframe**——分界在「内容在哪」。iframe 的内容在文件系统或远端，随时可变、无法回放、不受宿主控制；OpenUI 程序就在消息里，可回放、可主题化、可重渲染出同一结果。要让「能表达的东西」由组件目录承载，而不是让 Agent 造页面。

**相对 agent-sites 卡片**——分界在「扩展成本」。卡片是一形态一组件、一次发版；OpenUI 用一份 SDK 目录覆盖 N 种展示。卡片范式退场后，展示类需求没有理由再走它。

**相对 MCP Apps**——分界在**渲染器在谁的信任域执行**：

| 取舍项 | 宿主域渲染（本期主通道） | 沙箱域渲染（渲染器型 App） |
| --- | --- | --- |
| 组件与外观 | SDK 组件库，跟随宿主主题与设计 token | App 自带（如 shadcn），外观由 App 决定 |
| 第三方代码 | 无 | 有（沙箱 + CSP + 权限审批 + 审核） |
| 可回放 | 是（程序就是消息内容） | 程序可回放，运行环境不保证 |
| 组件丰富度 | 受 SDK 目录限制（32 个组件） | 由 App 决定，可超出宿主目录 |
| 跨宿主复用 | 只在本产品内 | 同一份程序可被第三方宿主渲染 |

判定规则：**只读展示、宿主自有产品 → 宿主域；跨宿主复用或需要第三方能力/组件库 → 沙箱 App。** 应用型 App（自带业务逻辑）只在工具卡片上，与本文通道不重叠。一句话分工：**「看起来是这样」用 OpenUI，「用起来是这样」用沙箱应用，「到别人的宿主里也得看起来是这样」用渲染器型 App。**

**顺带排除的两个近路**：

- 把 OpenUI 程序塞进 `<iframe srcdoc>`：iframe 里没有宿主 React 运行时，要用 SDK 组件就得把组件库搬进沙箱；且内容脱离消息文本，可回放与主题跟随一起丢掉。
- 把程序塞进自定义标签属性：标签属性都是字符串，体积、转义、流式与校验都不成立。

## 5. 组件目录与提示词：由 SDK 提供

原「自研类型生产线」「与 json-render 搭配」「peri-canvas 取材清单」随 2026-10-29 修订失效，不再维护。当前事实只有三条：

1. **目录在 SDK**：`@peri-code/sdk@0.3.0` 的 `src/openui/spec.json` 定义 32 个组件的签名、props schema 与提示词选项；宿主不复制、不改写，也不在运行时增删组件。
2. **提示词在 SDK**：服务端用 `generateOpenUISystemPrompt()` 生成系统提示词；宿主不再维护另一份「组件目录提示词」。
3. **技能是宿主资产**：`.agents/skills/openui/` 面向 Agent 用中文重述使用时机、语法、目录、动作与常见错误；`references/catalog.md` 与 spec.json 由同步测试钉住组件集合与必填参数。

**组件分组（32 个）**

| 分组 | 组件 | 数量 |
| --- | --- | --- |
| 布局与文本 | `Stack` `Row` `Grid` `Spacer` `Divider` `Text` `H1` `H2` `H3` `Code` `Link` `Pill` | 12 |
| 容器与数据 | `Card` `Callout` `DiffStats` `DiffView` `ChangedFiles` `Sources` `TodoList` `Table` | 8 |
| 指标与图表 | `Stat` `UsageBar` `Gauge` `BarChart` `LineChart` `PieChart` | 6 |
| 表单与动作 | `TextInput` `TextArea` `Checkbox` `Toggle` `Select` `Button` | 6 |

**必须随 SDK 一起遵守的约束**：`Stack` 是唯一 root；`Grid` 只能直接位于 `Stack` 下；`Row` 子项只能是叶子；`Card` 子项可为 `Row` 或叶子且不嵌套；图表每个 `series.data` 长度必须等于 `categories`；`Sources` 收 1–10 项；表单值必须由同卡片内的 `@ToAssistant` 按钮提交。

**同步门禁**：`packages/ui-components/web/__tests__/openui-skill-doc-sync.test.ts` 比对技能文档与 `OPENUI_ARTIFACT`——组件标题集合完全相等、每个必填参数出现在对应段落、示例围栏首条语句为 `root = Stack(` 且变量可达。

## 6. 落地与边界

**现状（2026-10-29 修订取代原切片计划）**

1. **已落地**：` ```openui ` 围栏 → `splitOpenUI` → 懒加载 `OpenUIRenderer` → SDK 渲染；解析失败、程序不完整或 props 校验失败时整段回退原文。
2. **已落地**：内置技能 `openui`（`.agents/skills/openui/`），含使用时机、32 组件目录、动作与 8 个完整示例；同步测试钉住文档与 `spec.json`。
3. **后续**：跟随 SDK 版本升级并回归历史消息渲染；旧 `ui-spec` 消息保持代码块展示，不做数据迁移。

**边界与不变量**

- **不可信输入**：OpenUI 程序是模型产物。字符串一律走文本节点，无 `dangerouslySetInnerHTML`、无 `rehype-raw`；外链只放行 http(s)；组件不发请求；环境上下文（`envId` 等）只能由宿主注入，程序不能读取或覆盖。
- **单围栏**：每个助手消息最多渲染一个顶层 `openui` 围栏；出现多个时整体回退 Markdown，避免模型用多个程序拼页面。
- **降级优先**：解析失败 / 程序不完整 / props 校验失败 → 回退整段消息原文（`data-openui-fallback` 标记原因），不整体崩、不静默丢内容；流式期间展示最近一次可解析版本。
- **主题桥**：只认 `--chat-code-bg` / `--chat-fg` / `--chat-link` 三个 hex 变量；非 hex 值回退 SDK 调色板，不在程序里开放颜色与样式。
- **可回滚**：渲染入口集中在 `OpenUIBlock`；撤销该分支即退化为普通代码块。

## 7. 风险与开放问题

| 项 | 说明 | 处理 |
| --- | --- | --- |
| 提示词漂移 | 交付给 Agent 的组件说明与 SDK spec 可能不一致 | `openui-skill-doc-sync` 测试钉住组件集合与必填参数 |
| 模型不守约 | 命名参数、无引用变量、root 缺失、图表长度不齐 | SDK parser 与 props 校验拦截，失败整段回退原文；技能给自检清单 |
| 数据膨胀 | 程序进入消息文本并随 Y.Doc 持久化 | 单围栏 + 渲染兜底；不自研限额，超长程序回退原文 |
| 小屏与可访问性 | 宽表、多序列图表在小屏退化 | SDK 组件自适应；宿主容器保持 `minWidth: 0` |
| 卡片退场后的承接 | `agent-sites` 下架后，站点结果的告知与入口由谁承载 | 由产品决策；若走本文通道，需评估 32 个组件是否够用 |
| 与 MCP Apps 的重叠 | 同一展示既能宿主域渲染、又能做成渲染器型 App | 按 §4 判定渲染域：只读展示、宿主自有产品走宿主域 |
| 生态收敛 | OpenUI / A2UI 的标准化速度未知 | 宿主只依赖 SDK 的稳定出口，渲染层可替换；不押注单一生态 |

## 8. 仍然有效的事实与契约

- 围栏语言是 `openui`；每个助手消息只渲染一个顶层围栏，多个围栏整体回退 Markdown。
- 内置技能名是 `openui`；旧 `ui-spec` 目录已删除，不再向 Agent 投放 JSON 组件树契约。
- SDK 版本钉在 `@peri-code/sdk@0.3.0`；32 个组件目录与服务端提示词随该版本发布。
- 旧 `ui-spec` 围栏只作历史兼容，按普通代码块展示，不迁移、不再校验。
- 宿主只维护围栏切分、懒加载、主题桥与动作回传；解析器与组件目录归 SDK。
