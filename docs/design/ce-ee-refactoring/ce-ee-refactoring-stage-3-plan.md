# CE 阶段 3：由用户排序的逐包适配执行计划

> **给执行智能体：** 此文件只在用户选定当前需要治理的包时使用。不从设计文档推断全仓适配顺序，不把其他包的目标顺手加入本次 PR。开始前读取当前包的 `refactor-plan.md`、真实源码/测试、[目标架构与开发规范](./ce-ee-engineering-standards.md)对应章节，并以该包的现有生产合同为约束。

**目标：** 根据用户确定的业务优先级及包依赖，逐个把物理分包后仍沿用历史逻辑的包适配到新的架构和开发规范。每完成一个包交付一个独立、经过审查、可上线的 PR，不阻断尚未适配包的业务迭代。

## 1. 任务领取及边界

1. 用户按业务需要和各包 `refactor-plan.md` 中的真实前置依赖指定当前包；执行者确认前置包状态，未经用户选择不更改优先级、不并行扩大到其他包。所有 plan 文件删除之前不声称全仓治理结束。
2. 为当前包单独补**详细实施任务**，核实原协议消费者、权限/组织隔离、Provider/Model 继承关系、数据库现存数据、Web 调用方、并发失败路径、部署和回滚要求。现有 `/api/*` 等外部稳定合同不能因目标 `/web/*` 设计而自动删除；旧 Environment/Chat 前端流程若要迁入后端，需要对应包明确批准的任务、接口兼容和浏览器 E2E，不能作为普通物理路径调整。
3. 当前包计划中明确需接入的新权限体系、接口资源规则、数据治理和模块公开边界，逐项确定允许修改的业务合同及对现有用户的影响；对超出本包的改动记录依赖任务，不在当前 PR 偷做。任何生产数据结构变化采用该包能单独上线的迁移与回滚策略，而非假设整个 CE 在同一窗口升级。

原总设计文档中的“按稳定 ID 治理 name CRUD、资源归属/visibility 与权限路径、隔离并行测试共享状态及测试专用注入”属于**逐包实施候选事项**，不再写成设计文档要求。真正选中该包时，依据它的 `refactor-plan.md`、生产消费者和真实缺陷单独生成技术任务；不得直接套用旧 M1 的文件级顺序，亦不得扩大至未选中的包。

## 2. 实施、审查与提交

每次按“实施 → 规格/质量 review → 修复 → 再 review”迭代至当前包无必须修复项；先运行最小专项测试，审查归零后运行该 PR 所需的完整 `bun run precheck`、前端修改时的 `bun run build:web`、真实数据库升级与关键 E2E。review 文档保留在工作区、不提交，供用户验收后手动删除。超出当前包的未来优化只记录，不拿全仓检查通过代替行为/合同核验。

通过可上线的包级验收后，在该包 PR 中删除其 `refactor-plan.md`，并向用户交付变更、测试、兼容/回滚证据。包未完成时不能提前删除其计划文件；无需适配的包经用户核查确认后也可删除其计划文件。每个包适配/确认后均可单独发布，常规开发和生产发布不要求等待其他包。

## 3. 全部完成标准

`packages/` 下所有包根目录的 `refactor-plan.md` 均因对应包已验收而被删除，且不存在未决的包级前置适配任务。没有旧式“冻结线上版本、最后一次切换”的全仓发布节点；用户可以持续调整余下包的治理优先级。
